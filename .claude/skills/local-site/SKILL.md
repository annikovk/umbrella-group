# Локальный стенд taxlab.ru

Одна команда из корня проекта:

```bash
tools/local-site.sh            # поднять и открыть в браузере
```

Дальше — `http://localhost:8088`, админка там же на `/wp-admin/`. Первый запуск
собирает образ и тянет базу (5–10 минут), последующие — 8 секунд.

## Что делает стенд

| | |
|---|---|
| Код | из зеркала `httpdocs/` как есть, смонтирован в контейнер |
| Docroot в контейнере | `/var/www/vhosts/taxlab.ru/httpdocs` — тот же путь, что на проде |
| PHP | 8.3 + Apache с mod_php (`docker/php/Dockerfile`) |
| База | MariaDB 10.11, дамп прода, пересоздаётся в `utf8mb3_general_ci` как на сервере |
| Конфигурация | `docker/` (compose, Dockerfile, php.ini, vhost, оверлеи) |
| Дампы | `.local-dev/db/` (в git не едут — там персональные данные из заявок) |

Путь docroot совпадает с продом не для красоты: WP Rocket, webp-express и часть
опций в БД держат абсолютные пути, и при совпадении копия ведёт себя как живой
сайт.

Прод-`wp-config.php` и `mu-plugins` не правятся — поверх них монтируются файлы
из `docker/overlay/`. Зеркало остаётся побайтовой копией сервера, а
`tools/sync-from-server.sh --delete` их не сносит.

## Команды

```bash
tools/local-site.sh                 # up: поднять, пустую базу залить дампом
tools/local-site.sh fresh           # файлы с сервера + свежий дамп + импорт (10–20 мин)
tools/local-site.sh db-pull         # только снять свежий дамп прода
tools/local-site.sh db-import       # залить последний дамп заново
tools/local-site.sh up --fresh-db   # поднять и перезалить базу из последнего дампа
tools/local-site.sh admin           # локальный админ local/local (пароли прода не подходят)
tools/local-site.sh status          # адрес, версия WP, размер базы, какой дамп залит
tools/local-site.sh logs -f         # логи Apache и PHP
tools/local-site.sh wp plugin list  # wp-cli внутри контейнера
tools/local-site.sh db              # клиент mariadb к локальной базе
tools/local-site.sh shell           # bash в web-контейнере
tools/local-site.sh down            # остановить (база остаётся)
tools/local-site.sh reset           # снести контейнеры и базу; файлы зеркала целы
tools/local-site.sh rebuild         # пересобрать образ (после правки php.ini/Dockerfile)
```

Флаги `--no-open` и `--fresh-db` работают и до команды, и после. В сессиях из
Telegram браузер не открывается и без флага (`CLAUDE_TG_DAEMON`).

Вывод wp-cli чистый только в stdout: предупреждения PHP уходят в stderr, так
что для разбора данных добавляй `2>/dev/null`.

Правки в `httpdocs/wp-content/themes/` видны сразу, перезапускать ничего не
нужно: `opcache.revalidate_freq=0`.

## Чем стенд отличается от прода

Это не баги, а осознанные отличия — все они в `docker/overlay/`:

- **Домен.** `WP_HOME`/`WP_SITEURL` перебиты на `http://localhost:8088`, а
  mu-plugin `zz-taxlab-local.php` переписывает `taxlab.ru` → `localhost:8088` в
  выводе страниц (в постах ссылки и картинки прописаны абсолютно). База при
  этом не тронута и остаётся копией прода. Остаться в HTML должен только
  `contact@taxlab.ru` — это адрес почты, и это нормально.
- **Погашены плагины**, которые лезут наружу или пишут в зеркало: WP Rocket,
  webp-express, WP Mail SMTP, Duplicator, Яндекс.Метрика, UTM-трекер. Список —
  константа `TAXLAB_LOCAL_DISABLED_PLUGINS` в mu-plugin, `active_plugins` в базе
  не меняется. Нужно посмотреть на сайт с WP Rocket — закомментируй строку.
- **Почта не уходит** (`pre_wp_mail` → true): в базе живые адреса из заявок.
- **`.htaccess` зеркала не читается** (`AllowOverride None`): там 301 на
  `https://taxlab.ru`, deny по трём IP и старый синтаксис order/allow. Правила
  пермалинков продублированы в `docker/apache/taxlab.conf`.
- **`protect918/` (антибот) и `F_F/` (adminer) закрыты** на уровне vhost,
  `protect918/code/include.php` из wp-config не подключается.
- **Внешние HTTP-запросы заблокированы** (`WP_HTTP_BLOCK_EXTERNAL`), иначе
  админка висит на проверках обновлений.
- **Пароли пользователей — прод-хэши.** Свой доступ: `tools/local-site.sh admin`.

## Гочи

- **`output_buffering = 14096` в `docker/php/php.ini` — трогать нельзя.** В
  `umbrella-group/functions.php` около строки 1093 стоит `?>`, потом пустые
  строки, потом снова `<?php`; эти переводы строк уходят в вывод раньше
  заголовков. На проде их глотает буфер из php.ini vhost'а (там ровно 14096), а
  в чистом `php:8.3-apache` буферизация выключена. Без этой строки ломается всё,
  что редиректит: `/wp-admin/` отдаёт 200 и пустое тело вместо 302 на логин.
- **ssh к прод-серверу идёт через Telegram-брокер** — `db-pull` и `fresh` могут
  ждать подтверждения в топике. Если ssh падает с «agent refused operation» —
  повтори попытку, брокер спросит разрешение.
- **Порт 8080 на машине занят** дашбордом, поэтому стенд на 8088. Менять — в
  `docker/.env` (`HTTP_PORT`, `DB_PORT`), файл личный и в git не едет.
- **Apache работает под uid/gid хозяина** (`HOST_UID`/`HOST_GID` в `.env`):
  зеркало лежит с правами 750 на владельце-человеке, `www-data` его не
  прочитает. При «403 Forbidden» на всём сайте — проверь эти переменные.
- **Дамп ~43 МБ в gzip**, импорт 1–3 минуты. Скрипт проверяет дамп на обрыв
  (`gzip -t` и «Dump completed» в хвосте) и хранит три последних.
- **В логах штатный шум темы** — `Undefined variable $hideforsmall`
  (`service-tiles.php:152`) на каждой странице и `headers already sent` в любой
  wp-cli команде (в CLI буфер невозможен). Это давние болячки темы, видные
  только потому, что здесь логи не прячутся; на работу стенда не влияют.
- **Стенд только читает прод.** Ничего обратно не заливается — правило проекта
  из CLAUDE.md остаётся в силе: код на сервер уезжает вручную.

## Если сломалось

1. `tools/local-site.sh status` — что вообще запущено.
2. `tools/local-site.sh logs --tail=50` — PHP-ошибки идут в лог контейнера, а не
   на страницу (`display_errors = Off`, чтобы вёрстку не рвало).
3. Нужны подробности WP — поставь `WP_DEBUG=1` в `docker/.env` и повтори
   `tools/local-site.sh up`: compose увидит новое значение и пересоздаст
   web-контейнер сам, `rebuild` не нужен. Вёрстка при этом не рвётся
   (`WP_DEBUG_DISPLAY = false`), всё идёт в лог.
4. База поехала — `tools/local-site.sh up --fresh-db` перезаливает её из дампа.
5. Всё с нуля — `tools/local-site.sh reset` и потом `fresh`.
